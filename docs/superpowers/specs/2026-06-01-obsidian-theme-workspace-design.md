# Obsidian 主题型收纳与沉淀机制设计

## 概述

本设计用于将用户的 Markdown 笔记、YouTube 链接和少量 PDF 等知识素材，沉淀到一个按主题组织的 Obsidian 知识库中。目标不是做“全盘文件归档”，而是建立一套低摩擦收集、半自动整理、可持续提炼、最终支持输出的知识工作台。

目标 vault 路径：

- `/Volumes/dockcase/kani‘s vibe coding world`

用户现状与约束：

- 主要素材是 `md` 文件与 YouTube 链接。
- 用户希望按主题组织知识，而不是按项目或课程作为一级结构。
- 用户希望同时保留“来源”和“提炼后的知识点”两层。
- `dockcase` 卷中存在大量不应自动吸收进知识库的噪音目录，例如 `node_modules`、`.git`、`.venv`、`dist`、照片和系统文件。

## 设计目标

1. 保留来源，避免只有观点没有出处。
2. 按主题组织，便于长期复用与输出。
3. 自动化承担重复劳动，但不越权替用户做最终判断。
4. 将“收集”和“沉淀”分离，避免知识库被半成品和噪音污染。
5. 让用户用自然语言即可驱动日常流程。

## 非目标

- 不做整个 `dockcase` 卷的无差别全盘扫描。
- 不搬运完整代码仓库及依赖产物进 vault。
- 不在首次版本中追求全自动卡片生成与全自动主题维护。
- 不把照片、视频和下载目录默认作为知识沉淀来源。

## 信息架构

知识库采用“主题优先、来源保留、卡片提炼、输出导向”的四层结构：

```text
/Volumes/dockcase/kani‘s vibe coding world
├── 00_收件箱
│   ├── md
│   ├── youtube
│   └── pdf
├── 10_来源笔记
│   ├── md
│   ├── youtube
│   └── pdf
├── 20_主题工作台
├── 21_主题卡片
├── 30_项目视图
├── 31_课程视图
├── 40_输出
└── 90_系统
    ├── _index.md
    ├── _log.md
    ├── _主题总表.md
    ├── _项目扫描清单.md
    └── _收件规则.md
```

各目录职责：

- `00_收件箱`：承接用户新丢入的原始材料，不要求当场分类或提炼。
- `10_来源笔记`：为每份素材生成标准来源页，保留出处、摘要和待提炼信息。
- `20_主题工作台`：按主题组织用户当前理解、问题、相关来源与核心卡片。
- `21_主题卡片`：保存最小知识单元，每张卡片只表达一个判断、方法或框架。
- `30_项目视图`：按项目反向汇总涉及的主题与资料，不作为主结构。
- `31_课程视图`：按课程或学习周期反向汇总内容，不作为主结构。
- `40_输出`：沉淀后的讲义、文章、方案、PRD 或分享稿。
- `90_系统`：放置索引、日志、规则和扫描配置。

## 三类核心页面

### 1. 来源页

来源页位于 `10_来源笔记`，一篇 `md`、一个 YouTube 链接、一个 PDF 各自先对应一条来源页。

来源页职责：

- 记录素材是什么。
- 记录素材从哪里来。
- 给出 3-8 条摘要。
- 标记候选主题。
- 说明下一步可提炼方向。

建议模板：

```md
---
type: source
source_kind: md
source_path: /absolute/path/to/file.md
source_url:
themes:
  - AI产品判断
  - JTBD
status: 待提炼
---

# 来源 - 示例标题

## 内容摘要
- ...

## 关键原话
- ...

## 可提炼主题
- [[AI产品判断]]

## 下一步
- 拆成 2-3 张主题卡
```

### 2. 主题页

主题页位于 `20_主题工作台`，按主题长期生长，不负责保存原始全文，而负责组织理解、问题、卡片和相关来源。

主题页职责：

- 定义当前主题的核心理解。
- 汇总已经沉淀出的卡片。
- 链接相关来源页。
- 记录未解问题。
- 指向潜在输出方向。

建议模板：

```md
---
type: theme
---

# AI产品判断

## 当前判断
...

## 核心卡片
- [[tiny core 比功能堆砌更重要]]

## 相关来源
- [[来源 - 示例标题]]

## 未解问题
- ...

## 可输出方向
- 课程讲义
```

### 3. 卡片页

卡片页位于 `21_主题卡片`，每张卡片只保留一个可复用知识点。

卡片页职责：

- 表达一个明确判断或框架。
- 解释其理由、适用场景和边界。
- 回链来源页与主题页。

建议模板：

```md
---
type: card
themes:
  - AI产品判断
sources:
  - [[来源 - 示例标题]]
status: 正式
---

# tiny core 比功能堆砌更重要

## 结论
...

## 为什么
...

## 适用场景
- ...

## 反例或边界
- ...
```

## 命名规则

以可读性优先，避免过度编号。

- 原始文件：保留原名。
- 来源页：`来源 - 原始标题.md`
- 主题页：直接使用主题名，例如 `AI产品判断.md`
- 卡片页：直接使用完整判断句，例如 `95% 自动化不等于真正可交付.md`
- 输出页：`输出 - 主题或用途.md`

命名原则：

- 让用户通过中文语义搜索即可找到内容。
- 通过“来源 - ”前缀将原始材料与沉淀内容肉眼区分。
- 主题页和卡片页不加日期，保持长期可生长属性。

## 收纳边界与扫描规则

系统必须区分“可沉淀资料”和“噪音目录”。

### 允许进入系统的资料

- `md`
- YouTube 链接
- `pdf`
- 少量 `docx`、`pptx` 等手动选入的资料
- 用户明确登记的项目目录中的 `README`、`docs/`、`spec`、`plan`、`notes` 等文档内容

### 默认忽略的目录和文件

- `node_modules`
- `.git`
- `.venv`
- `dist`
- `build`
- `coverage`
- 照片、视频和大体量相册目录
- 系统隐藏文件如 `._*`、`.DS_Store`
- 未经明确登记的整个下载目录和系统目录

### 三条入口

1. 手动收件入口
   用户主动将 `md`、链接和资料放入 `00_收件箱`。
2. 项目扫描入口
   只扫描用户明确登记在 `_项目扫描清单.md` 中的项目目录，并只提取文档类内容。
3. 忽略入口
   对于噪音目录永久不进入知识库自动化流程。

## 自动化设计

系统采用半自动流水线，而不是一键全自动沉淀。

整体流程：

```text
00_收件箱 -> 生成来源页 -> 候选主题/候选卡片 -> 用户确认 -> 正式沉淀
```

### 第一层：完全自动

- 根据类型整理收件内容到 `00_收件箱/md`、`youtube`、`pdf`
- 为每条素材自动生成来源页
- 自动提取基础元信息：
  - 标题
  - 来源类型
  - 原路径或原链接
  - 创建时间
  - 初步摘要
  - 候选主题
  - 状态 `待提炼`

### 第二层：自动建议

系统提出但不直接写入正式沉淀层的内容：

- 候选主题
- 候选卡片
- 候选关联关系

这些候选内容必须带有 `待确认` 语义，避免系统越权创建大量低质量卡片。

### 第三层：确认后写入

只有在用户确认后，系统才执行：

- 正式创建或更新主题页
- 正式创建或更新卡片页
- 更新项目视图和课程视图
- 更新来源页状态为 `已提炼`
- 追加系统日志

## 状态流转

来源页建议状态：

- `待整理`
- `待提炼`
- `待确认`
- `已提炼`
- `已归档`

卡片页建议状态：

- `候选`
- `正式`

主题页不需要复杂状态，重点在于长期持续更新。

## 用户交互模型

系统应允许用户用简单口令驱动流程，减少方法负担。

建议支持的核心操作语句：

- `帮我收这个`
- `帮我整理收件箱`
- `帮我把这篇变成来源页`
- `帮我提炼这篇的主题和卡片`
- `帮我更新 AI产品判断 这个主题页`
- `帮我把这个主题整理成输出`

这些语句的目标是让用户只表达意图，不必记忆内部步骤。

## 使用节奏

推荐节奏：

- 日常：随手把素材放入 `00_收件箱`
- 每周 1-2 次：集中整理收件箱，生成来源页与候选卡片
- 每两周或每完成一个主题：从主题页产出讲义、方案、课程稿或项目总结

这使系统从“先整理再学习”变成“先收集，再整理，需要时输出”。

## 示例映射

示例素材：

- `/Users/helenahe/Desktop/Builder 自学内容 Week1 · V0.5 想清楚与搭助理.md`

进入系统后的目标路径：

- 原文件进入 `00_收件箱/md/`
- 生成来源页：
  - `10_来源笔记/md/来源 - Builder 自学内容 Week1 · V0.5 想清楚与搭助理.md`
- 生成候选主题：
  - `AI产品判断`
  - `JTBD`
  - `Agent设计原则`
- 生成候选卡片：
  - `tiny core 比功能堆砌更重要`
  - `95% 自动化不等于真正可交付`
  - `Research Preview 适合低承诺高反馈验证`

## 风险与控制

### 风险 1：主题页膨胀

控制方式：

- 主题页只做工作台和导航，不承载过多正文。
- 将具体判断拆到 `21_主题卡片`。

### 风险 2：自动化制造废卡

控制方式：

- 自动化只提建议，不直接写正式卡片。
- 由用户确认后再落盘。

### 风险 3：噪音目录污染知识库

控制方式：

- 采用白名单式入口。
- 将项目扫描限制在文档型内容。

### 风险 4：来源与沉淀脱节

控制方式：

- 每张卡片必须回链来源页。
- 每个主题页必须保留来源区块。

## 测试与验收

最小验收标准：

1. 可以成功初始化 vault 目录结构和系统文件。
2. 可以接收一个 Markdown 文件并生成标准来源页。
3. 可以从来源页提出候选主题和候选卡片。
4. 在用户确认后，可以创建至少一个主题页和一张正式卡片页。
5. 可以通过主题页反查相关来源和卡片。

后续扩展验收：

- 支持批量导入多个 Markdown 文件。
- 支持 YouTube 链接标准化入库。
- 支持项目扫描清单驱动的文档扫描。

## 实施顺序

建议按以下顺序实施：

1. 初始化 vault 目录和 `90_系统` 文件
2. 建立收件规则和来源页模板
3. 用单篇示例 Markdown 跑通 `收件 -> 来源页`
4. 加上候选主题和候选卡片生成
5. 再实现用户确认后的正式沉淀
6. 最后再考虑项目扫描清单和批量流程

这样可以先跑通最小闭环，再逐步增加自动化能力。
